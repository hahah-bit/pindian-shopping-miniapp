## R01 / P1：幂等查重可把内部备注返回用户

`conversation-usecases.ts:75` 按会话和 `clientMessageId` 查重，不区分发送人和可见性；重复记录直接返回。小程序发送控制器将其 content 原样响应。

真实 HTTP 复现：客服先发送内部备注 `clientMessageId="ag-note"`；用户向自己的会话发送普通文本但使用相同 ID，得到 HTTP 201、`duplicated=true`、`sender="agent", kind="note", content.text="内部备注：老客户"`。GET 历史的过滤不能保护 POST 重复响应。

幂等范围必须包含发送者身份；处理重复、历史、卡片等所有响应时都应再次保证可见性，避免用户读取客服内部记录或客服间幂等碰撞。补回归覆盖跨发送者 ID 碰撞、内部备注、相同键不同载荷及结束后重试。

## R02 / P1：工单与订单归属、退款资格及原因未校验

`CreateTicketUseCase` 不验证关联订单是否属于用户。`RequestTicketRefundUseCase` 不验证输入订单与工单用户及关联订单一致。装配 `CS_REFUND_PORT` 的资格校验只有支付 succeeded，创建退款时将原因固定为 `group_failed`，未按 spec 校验组状态/取消或售后资格。

真实 HTTP 复现：用户 B 为用户 A 的已支付订单创建工单（201）；后台受理（201）并发起退款（201）。落库事实为 `ticket_user=B, order_user=A, group_status=success, reason=group_failed, refund_status=requested`。本轮没有实际驱动渠道，但 Worker 会处理这类已落库的退款请求。

应通过公开业务用例验证订单归属、关联范围、售后资格、操作权限与审批决策，使用真实业务退款原因；不把“有支付事实”视为任意工单可退款，也不假造拼单失败。验证成功/失败组、不同用户/订单、已发货/完成及累计退款边界。核查并解决 D017 的业务授权来源。

## R03 / P1：退款与工单并非同事务，故障后留孤立退款

`ticket-coordination.ts:31` 调用退款端口时未传工单事务；`foundation.module.ts` 也没有把 `sessionTx` 传给已有 `CreateFullRefundUseCase`。退款仓储使用另一连接提交，后续工单失败不能撤回退款。

真实 PG/HTTP 复现：在 `after_sales_ticket_actions` 的 `request_refund` 插入前注入失败。请求返回 HTTP 500；数据库仍有 **1 张退款单**，工单 `related_refund_id=null`、退款 action **0 条**。接口失败后退款请求仍可被 Worker 驱动，且重试会遇到已有退款记录。

明确跨域一致性边界：单进程同库可通过公开接口贯穿事务，或使用持久化协调记录、可靠事件与可恢复补偿。不能仅回滚工单后声称整体回滚。补生产装配故障测试、结果查询、恢复重试、幂等和审计证据。

## R04 / P1：承诺的客服及工单页面没有完整交付，补发接口不存在

源码检查：`AdminCsView.vue` 仅有排队/我的会话列表与接入按钮，没有聊天详情、消息回复、图片/卡片、转接、内部备注、结束和转工单操作。页面文案宣称“下方会话处理”，实际没有相应内容。后台售后导航仍无已实现的工单操作页。

小程序会话页只有文本发送，将图片显示为 `[图片]`、卡片显示为类型占位文本，没有可操作图片上传/预览及业务卡片呈现。客服中心仅展示工单列表，缺少提交、详情、处理答复和反馈流程。请求封装不等于可使用页面。

spec 承诺的 `/api/admin/v1/after-sales/tickets/:id/reshipment` 真实请求返回 **404**；不存在协调用例、入口和生产接线，不能将 F034/F035 写为全部完成。

按原需求与整体 spec 补齐两端流程、历史入口、权限、加载/空态/错误/重试与操作反馈；图片权限和存储必须落实。以有数据的完整用户→客服→工单→退款/补发路径验收，而不只验证接入按钮。

## R05 / P1：工单处理和用户反馈状态机与 spec 不一致

真实 HTTP 复现：工单 accept 后进入 processing，再 reply 返回 **409 TICKET_STATE_CONFLICT**。`ProcessTicketUseCase` 将 reply 映射为 transition(processing)，而聚合只允许 open→processing，导致最常见的处理中回复不能执行。

用户反馈 `satisfied=false` 后工单仍为 resolved，没有 spec 所要求的重新进入 processing；用户详情响应缺少 actions，无法读取管理员处理答复。聚合把 resolved 当不可迁移终态，也不能实现 D017 文档的 resolved→closed。

先将业务决策、DDD、spec、状态图统一，再实现处理/等待反馈/解决/继续追问/关闭与幂等。用户只应看到授权的处理记录，内部备注仍不可见。补关键状态全路径回归和前端验证。

## R06 / P1：客服在线状态和自动分配只是占位

真实 HTTP 复现：POST heartbeat 返回 200，但 `cs_agent_presence` **0 行**。有心跳后新会话仍 queued/hasAgent=false。代码中无在线心跳写入、到期处理、接待量选择及自动分配路径；accept 只是将请求人设为接待者。转接也不检查目标在线、启用状态及客服权限。

原需求要求新会话自动分配在线且接待量较少的客服，不能未经授权改为人工接入建议。现有角色只有 super_admin/catalog_admin，`agent:manage` 仅超级管理员拥有，普通客服/主管权限及其分配范围没有落实。

落实在线状态、超时、负载分配、并发接入/转接和角色范围；测试两个不同客服、离线及无权限管理员。现有“两个并发接入”集成使用同一个超级管理员 token，不能证明不同客服的分配和访问边界。

## R07 / P1：分页后过滤内部消息导致用户补取停滞

仓储先按 seq 取最多 50 条，再由应用过滤内部备注。小程序游标取最后一条可见消息 seq。真实 HTTP 复现：会话 seq 1–50 全为内部备注，seq 51 为公开回复。用户 afterSeq=0 连续两次 GET 均返回 **messages=[]、lastSeq=51**；前端游标仍为 0，公开回复永远无法收到。

在查询分页边界中按授权过滤或设计可靠的扫描游标；区分页尾游标、会话最大 seq 和已读位点，防止过滤后的空页卡住或跳过未取消息。补多页、内部消息、并发增量及断线恢复验证。消息已读确认目前也没有对应持久化机制，不能将 seq 当已读证据。

## R08 / P2：卡片投影故障与消息引用权限未贯通

真实 HTTP：上架商品的 `/cards/product/:id` 返回 **500**，因为投影访问实际 ProductState 不存在的 `state.snapshot`；主图字段也与现有模型不同。用户 B 可以把用户 A 的订单 ID 作为会话卡片发送（**201**），发送路径只检 UUID，没有用投影可见性验证引用；直接读取 A 的订单卡片虽 404，不能代替消息发送与接收时的授权。

按真实公开契约接入产品/订单/组/退款投影，发送、渲染和刷新均校验权限，图片验证资源存在、归属与访问范围。回归覆盖四类卡片、下架、他人引用与失效资源。

## R09 / P2：并发恢复会话违反幂等承诺

真实 PG/HTTP：在插入会话时注入 150ms 延迟，同一用户并发 POST 创建，结果 **201 + 500**，一张开放会话唯一约束阻止重复落库，但未把冲突恢复成同一会话响应。唯一约束避免重复并不等于请求幂等。

原子创建/查找或在唯一冲突后重新读取本人会话，返回一致结果；回归验证两个请求同 ID、无 500、合法状态，勿吞掉无关数据库异常。
