## 必须处理的问题

### R01 / P1：数量换算忽略商品单位

`fulfillment-generation.task.ts:47` 只将整件数量文本交给 `wholeQuantityToGrams`，后者一律乘以 500；商品目录允许自由填写单位，需求也明确存在斤、克、件、箱等。独立测试将成功组不可变快照设为 `wholeQuantityText="10", unit="克"`，两笔 30 份额订单得到 `[2500,2500]` 克，合计 **5000 克**，实际整件仅 **10 克**。小程序还把换算后的斤文本与原始单位拼接，后台则固定显示斤。

必须先确定支持的单位、精度和不可分配商品规则，再按快照单位精确换算；不能擅自收窄已有商品支持范围。历史组快照、数据范围和迁移兼容均需处理，禁止通过当前商品改配置静默修改历史交易。

### R02 / P1：关键业务决策未确认却已实施

README、spec 和 D011–D015 明确写为“建议方案、待用户确认”，同时 README 把阻塞项写为“无”、任务写为“已完成”。数量粒度和尾差、生成时机、包裹与补发、完成权限、改址规则均已进入代码。仓库根 AGENTS.md 第 2.6、7.3、8 节要求依赖此类歧义的实现前取得明确决策，策略可替换不代表已获确认。

核查已有用户确认来源；不存在来源时将依赖项恢复待决策，向用户提出具体可比较方案，确认后更新 DDD/spec/plan 并调整实现。未取得确认前不得把当前规则记为已确认。

### R03 / P2：后台普通详情仍返回明文电话

`admin-fulfillment-queries.ts:147` 无条件返回 `phone: row.receiver_phone`，即使 `unmasked` 未启用。真实 HTTP 返回同时包含 `phone="13800001230"` 和 `phoneMasked="138****1230"`。页面隐藏明文不构成服务端脱敏，且与接口注释及 spec 的电话访问边界不符。

普通响应去除明文；发货必需的明文通过明确授权、审计的查询或导出路径获取。测试断言普通响应不含完整号码，而不只检查存在星号。

### R04 / P1：审计失败导致发货结果与响应不一致

`admin-fulfillment.ts:42–56` 在发货事务提交后写审计。独立探测注入审计失败，应用用例抛出 `independent audit down`，但数据库已有包裹且 `shipped_quantity_grams=100, status=partially_shipped`。管理端会收到失败反馈，而发货已生效且审计缺失；改址及管理员完成也采用相同先提交再审计的结构。

按设计实现业务操作与审计的可靠一致性（同事务，或有持久化保证的事件/outbox 与补偿）；定义重试及结果查询语义，测试实际落库及故障恢复，避免报错后用户换运单重复发货。

### R05 / P2：后台缺少已承诺的操作入口

`AdminFulfillmentView.vue` 仅接入组列表、详情、发货/补发和导出；没有管理员改址表单、版本反馈、标记完成操作。`completeFulfillmentOrder` 虽有请求封装，页面没有调用。现有开发验收记录只有无成功组情况下的空态浏览，不能证明这些操作已交付。

按已确认 spec 补齐操作、权限、加载/错误/重试反馈，并用隔离有数据环境验证部分发货、改址、完成、导出与刷新。不得用 HTTP 接口测试替代后台页面交互。

### R06 / P2：首次补发破坏进度及地址锁定

独立探测对 `pending_shipment` 单先创建补发：非补发已发数量仍为 0，但聚合状态变成 `partially_shipped`；随后改址成功。`addShipment` 总按数量重新计算状态，而 `updateReceiver` 仅检查非补发数量，不能覆盖“已存在补发包裹”的地址锁定边界。

先确认补发资格、是否必须关联原包裹、收货信息锁定条件及完成后补发边界，再补失败优先的领域与真实 PG 回归。至少保持“补发不改变主发货进度”与发货事实一致。
