# D-007 已支付订单取消与成功判定竞争

状态：**已确认（2026-10-01 用户选定方案 A：先到先得 + 申请即扣容量）**。关联：需求 §2.8、T004 D005。

## 背景

预占未支付可自由取消（T004 已实现）。支付生效后：
- 组内还有其他单位未支付（组未成功）→ 用户想取消 = 取消已支付订单 → 全额退款（需求 §2.8 允许，"拼单成功前允许主动取消"）。
- 组恰好因这笔支付达到 60 单位 → 同一时刻"支付生效"与"取消申请"竞争。

## 方案 A（推荐）：先到先得，以事务提交顺序为唯一裁决；成功后只能售后

- **取消资格**：仅 `组 status=open` 时允许发起已支付订单取消（发起后进入"退款中"，组容量立即扣除该笔单位——取消申请即生效，退款是异步结果）。
- **竞争裁决**：取消申请与支付生效都在组行锁事务内：
  - 支付生效事务先提交 → 组可能变 success → 取消请求看到 `status=success` → 拒绝，返回"拼单已成功，请走售后"（本阶段售后工单未建，仅提示后续开放）；
  - 取消事务先提交 → 组容量回落 → 后到的支付生效：**本单已被取消，渠道支付事实存在但订单已取消 → 进入"已取消但收到付款"异常**（见 D-008 迟到支付处理）。
- **取消截止**：组 `success/failed` 即截止；`failed` 后无需取消（组失败自动全额退款，见 D-009）。
- **退款申请即锁容量**：取消已支付订单时先扣组 paidUnits（防成功判定与退款窗口重叠），退款失败进入重试/人工，**不自动回滚容量**（容量已让给其他买家，回滚会超卖；退款失败走人工退款或转售后）。

**案例**：组 40 单位已支付 + 用户 X 预占 20 未支付。用户 Y 支付最后一单 20：
- Y 的支付生效先提交 → 组 success（60）→ X 此刻点取消 → 拒绝"已成功，走售后"；
- X 在 Y 生效前提交取消 → X 的 20 单位退出（paid 40→20）→ 组回 open → Y 的支付生效仍可完成（capacity 40→60，Y 是最后单）→ 组 success。X 的退款异步进行。

## 方案 B：取消申请进入"待确认"宽限期，期间冻结组成功判定

窗口期内新支付被拒。**否决**：窗口长度无法定义（多长都任意），且冻结组成功伤害其他买家；需求未要求。

## 方案 C：成功后仍允许取消并触发整组解散

伤害其他已支付买家，需求明确"成功后不能直接取消，需通过售后"。**否决**。

## 影响（A）

- 退款单聚合 `Refund`（申请/受理/处理中/成功/失败）；取消已支付订单 = 建退款单 + 扣容量，同事务。
- 组 `open` 时取消已支付订单：`paidUnits −= units`、`paidAmountFen/goods −=`（报价快照金额）。
- 渠道退款结果异步确认（D-009）。
