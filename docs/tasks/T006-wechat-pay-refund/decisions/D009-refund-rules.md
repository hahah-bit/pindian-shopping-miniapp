# D-009 退款规则与库存/组衔接

状态：**已确认（2026-10-01 用户选定方案 A：五态退款 + 渠道驱动 + 幂等）**。关联：需求 §2.8/§2.9、AGENTS §7.2、D-007/D-008。

## 背景

三类退款触发：① 预占未支付——无需退款（无支付事实）；② 已支付订单在组 open 时的用户取消（D-007）→ 全额退款；③ 组截止失败时全部有效支付订单 → 全额退款。退款依据**支付事实**（Payment 实付金额），不按商品当前价重算。

## 方案 A（推荐）：申请/受理/处理中/成功/失败五态 + 渠道驱动 + 幂等

- **触发与建模**：
  - 用户取消已支付订单（组 open）→ 同事务：扣组容量 + 建 Refund（`requested`）；
  - 组截止失败 → 失败流程为每笔有效支付订单建 Refund（`requested`）；
  - 迟到支付（D-008）→ 建 Refund（`requested`，原因 late_payment）。
- **执行**：Worker 把 `requested → submitted`（调渠道申请退款），渠道受理 → `processing`；回调成功 → `succeeded`（终态）；回调/查询失败 → 指数退避重试（上限 N 次）→ 超限 `failed` + **人工处理队列**（后台可见、可安全重试）。
- **安全重试条件**：仅当渠道查询确认"未受理或受理失败"才可重新提交；渠道单号（out_refund_no）按退款单固定，**同一退款单对微信是幂等键**——重复提交同号不会重复退款（微信按 out_refund_no 幂等）。
- **累计上限**：`Σ(该支付单下 succeeded+processing 的退款) ≤ 实付金额`，数据库层按支付单汇总校验 + 应用层事务内断言。
- **无渠道完成证据不显示已退款**：`succeeded` 仅由渠道回调或查询确认写入。
- **库存/组衔接（沿用 T004 已确认规则 + 本决策新增边界）**：
  - 沿用：组 open 时用户取消已支付 → 申请即扣组容量（D-007）；组截止失败 → 组 failed + 整件释放（T004 D002）+ 全员退款；
  - **新增边界**：退款失败不回滚容量/组状态（容量已让渡，回滚会超卖）；退款失败走人工，不阻塞组继续拼单或成功；组 success 与退款进行中互不阻塞（A 组成员退款期间 B 的新预占/支付照常）。

**案例**：组截止失败，3 笔已支付订单（16833/16833/16834）→ 3 张退款单 `requested` → Worker 提交渠道 → 2 笔回调成功 `succeeded`，1 笔渠道返回"受理中"→ `processing` → 查询确认成功 → `succeeded`。Σ退款 = Σ实付。

## 方案 B：申请即调渠道同步等结果

把渠道调用放进用户请求路径。**否决**：外部超时属结果未知，同步等待会阻塞用户且容易重复提交；必须异步。

## 方案 C：失败退款自动转余额/优惠券

无此需求，引入资金复杂度。**否决**。

## 影响（A）

- Refund 聚合（五态+原因+渠道单号+重试计数）；payments 出站端口 `RefundChannelPort`（submit/query）。
- 后台：退款列表/详情/失败重试（权限+原因+审计）。
- Worker：退款驱动任务（与到期/截止任务共用循环，职责互斥——各自只处理自己状态的记录）。
