# D-010 支付查询补偿与 Worker 协调

状态：**已确认（2026-10-01 用户选定方案 A：单 Worker 五任务 + 全部 DB 驱动）**。关联：需求 §10、T004 F016（已有到期/截止任务）。

## 背景

微信支付结果通过两条途径到达：支付回调（主）与主动查询（补偿）。回调可能丢失、迟到或乱序；发起支付时外部请求可能超时（结果未知）。T004 Worker 已有预占过期/组截止任务，本阶段新增支付/退款任务必须与它们协调而不冲突。

## 方案 A（推荐）：单 Worker 循环 + 五个互斥状态任务 + 全部 DB 驱动

Worker 单循环内依次执行（各自 try/catch，互不阻断）：
1. **预占过期**（T004 已有）；
2. **组截止**（T004 已有）；
3. **支付查询补偿**：`Payment` 处于 `unknown/processing` 且超过 N 秒未更新 → 调渠道查询；结果 `success` → 应用支付生效流程（与回调同一幂等入口）；`closed/notpay` 且订单 unpaid 且预占过期 → 订单 expired（正常到期路径接管）；多次查询仍未知 → 退避重试，超限进入人工队列。
4. **退款驱动**（D-009）：requested → 提交；processing → 查询；失败重试退避。
5. **人工异常队列清理提示**（只读统计，供后台展示）。

- **外部调用与事务边界**：任何微信 HTTP 调用都在数据库事务之外；渠道结果入库用短事务 + 幂等键（channel transaction id 唯一、out_refund_no 唯一）。
- **回调与查询竞争**：同一支付事实的生效流程以 `payment_transactions` 表唯一约束 + 行锁保证只应用一次；回调先到就生效并标记来源 callback，查询后到发现已 applied 直接返回。
- **重启恢复**：所有任务状态在 DB（无内存队列），Worker 重启后下一轮扫描继续。
- **可靠投递**：本阶段对外无主动通知用户义务（站内状态即投递）；渠道侧我们作为接收方的幂等已覆盖，作为发起方的退款结果以查询补偿兜底。

## 方案 B：引入消息队列/定时调度库

超出单实例架构现状。**否决**。

## 方案 C：回调信任化（收到回调即终态，不查询）

回调可能丢失。**否决**：查询补偿是需求 §10 明确要求。

## 影响（A）

- `payment_transactions`（渠道事实，含原始通知密文证据）、`payments`（聚合）、`refunds` 表；回调端点 `/api/payments/v1/notify`（平台证书验签，公开路由但签名校验）。
- Worker 扩展为五任务循环；配置化轮询间隔与重试上限。
