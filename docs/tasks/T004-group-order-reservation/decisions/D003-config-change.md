# D-003 商品配置变化对既有组的影响

状态：**已确认（2026-09-30 用户选定方案 A）**。关联：AGENTS §8"配置变化"。

## 背景

组存续期间（可能数小时到数天），管理员可能改价、改允许份额、下架商品。哪些规则在组创建时固化？

## 方案 A（推荐）：组快照固化 + 当前可售状态门禁

- **组创建时固化 `salePolicySnapshot`**：原价 P、允许份额集合、整件数量、计量单位、整件参考价（P+500）。组存续期间，匹配、可完成性、报价一律按**组快照**计算，与商品当前配置无关。
- **商品改价/改份额**：只影响**新创建的组**；已有组按快照继续运行到截止或成功。
- **商品下架**：已有组继续运行（保护已下单用户），但**不再接受新预占**（预占写入路径检查商品当前 `status='on_shelf'`，失败返回 `PRODUCT_NOT_ON_SHELF`）。已在组内的未支付预占可继续支付。
- **商品重新上架**：恢复接受新预占。

**案例**：组 G1（快照 P=50000，允许 1/2、1/3）。管理员把商品改为 P=60000 且只允许 1/2。用户 X 预占 G1 的 1/3 → **成功**（按组快照报价 16833）——因为 G1 快照允许 1/3；新组 G2 按 P=60000 创建。管理员随后下架商品 → 新用户 Y 预占 G1 → 拒绝（商品已下架）；X 的预占不受影响可支付。

## 方案 B（替代）：跟随商品当前配置

组不存快照，每次匹配/报价实时读商品。问题：改价会使进行中组的报价漂移，用户下单价与打开页时不一致；改份额可能让已形成的组合变得"不可完成"，违反组内自洽。**不推荐**。

## 方案 C（替代）：改配置时强制解散所有进行中组

影响已下单用户，需要整组退款（支付未接入前是预占取消）。复杂且伤害体验，需求未要求。**不推荐**。

## 影响

方案 A 影响：groups 表新增 `sale_policy_snapshot` jsonb；可完成性/报价用例读组快照而非商品聚合；预占写入前检查商品 status。
