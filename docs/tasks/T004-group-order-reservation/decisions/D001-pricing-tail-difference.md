# D-001 报价固定时点与尾差承担

状态：**已确认（2026-09-30 用户选定方案 A）**。关联：需求文档 §2.5、AGENTS §7.2/§8、T004 spec。

## 背景

用户端整件价 = P + 500 分。份额应付按比例分摊时可能出现不可整除（如 P=50000：1/3 = half-up(50500/3) = 16833，三单合计 50499 ≠ 50500）。需求要求"整组订单金额合计严格等于整件价，最后一个完成拼单的订单自动补差额"。本项目为"立即支付"模式（选份额→下单→支付），报价必须在下单时固定，不能支付时改价。

## 方案 A（推荐）：下单预占时判定"最后单"并固定补差报价

- 通用报价：`应付 = half-up((P+500) × units / 60)`，与商品页参考价同公式。
- **最后单判定**：下单预占时，若 `已生效支付单位 + 其他有效预占单位 + 我的单位 == 60`，我是唯一可能的"补差单"（容量约束保证唯一性）：
  - 我的应付 = 整件价 − 组内已生效订单应付合计 − 0（其他预占未支付，不计入）；
  - 同时商品部分 = P − 已生效订单商品部分合计；服务费部分 = 应付 − 商品部分（保证商品合计=P、服务费合计=500，分别可追溯）。
- 非最后单按通用报价；补差价可能比通用价多或少 1–2 分，下单页面明确展示"含尾差调整"。
- 守恒验证：任何时刻 组内已生效订单应付合计 ≤ 整件价；组成功当且仅当合计 == 整件价且单位 == 60。

**案例**：P=50000。① 1/3+1/3+1/3：前两单各 16833，第三单为最后单，报价 = 50500−16833−16833 = **16834**。② 1/2+1/2：各 25250，无尾差。③ 40 单位已生效（1/2=25250，商品 25000+服务费 250；1/4=12625，商品 12500+服务费 125）+ 1/5 最后单：应付 = 50500−25250−12625 = **12625**，商品部分 = 50000−25000−12500 = 12500，服务费 = 125——恰好无尾差。④ 1/3+1/3+1/4 组合不可行（剩 10 单位不可完成），匹配层拒绝。

**取消重组**：补差单未支付过期/取消 → 释放 → 组回 open，下一个填满者重新按公式计算，天然守恒。已支付订单永远不重算。

## 方案 B（替代）：固定 half-up 价 + 平台补贴/收取零头

组内全部按通用 half-up 价，合计差 1–2 分由平台承担（或少收）。优点：报价逻辑最简单。缺点：违反需求"合计严格等于整件价"的明确要求；平台服务费收入不可精确核算。**不推荐**。

## 方案 C（替代）：支付时调整最后单金额

下单按通用价，支付生效时若是最后单改为补差价。**不可行**：微信支付下单金额已锁定，不能二次改价；且"立即支付"模式中预占与支付几乎同时，改价窗口会造成金额不一致。**否决**。

## 影响

方案 A 影响：订单须存 `priceSnapshot`（通用价、尾差调整额、商品/服务费拆分）；组聚合须暴露"当前占用单位与已生效金额合计"供最后单判定；预占创建与最后单判定须同事务（容量与金额守恒原子）。
